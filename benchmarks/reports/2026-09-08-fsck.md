# Full repository fsck at the cache cutoff — 2026-09-08

The indexed object-scan fix improves full `fsck --audit-only` at 65,601 records from a median **23.047 s to 9.529 s** when the metadata cache is exceeded: **2.42× faster, −58.65%**. This is the complete CLI command, including repository open and teardown, on a verified packed repository.

The next significant cost is traversal state spilling to SQLite. On the fixed revision, keeping the record cache but spilling the traversal sets takes **7.154 s**, versus **0.870 s** with both in memory. A separate CPU profile attributes **23.45% of sampled user-mode cycles** to SQL parsing, translation, and bytecode construction. Statement reuse in `SpillSet` is the next targeted optimization; it has not been implemented in this change.

## What the cutoff means

For a fixture containing N records:

- Limit N−1 discards the metadata cache and uses the ordered object stream; traversal sets also spill.
- Limit N retains all cached records, while traversal sets spill upon reaching N entries.
- Limit N+1 retains the record cache and traversal sets in memory.

This separates the adjacent cache and spill transitions. Fsck's default object limit is 250,000; the 65,536-record physical scan window is a separate bound. This investigation varies the configured limit around each fixture's actual count. The permanent frontier case contains exactly 250,000 records but was not executed in this run.

The fixtures contain unique small file payloads, directory records, one retained root, real packed storage, and no corruption or unreachable garbage. Standard cases use 8,192 and 65,536 files plus 65 directory records. These results describe healthy full repository auditing on this workload; they do not measure repair, concurrent writers, or large-payload throughput.

## Profiling the remaining work

A separate `perf record -F 999 -e cycles:u` run measured the fixed CLI at 65,601 records with memory limit 65,601, preserving the record cache while forcing spill. Its healthy report checked the same root, 65,601 records and payloads, and unchanged revision. The profile collected 9,007 samples with zero lost samples. Profiler timings are excluded from the table.

Identifiable self-cycle shares were 5.70% in `turso_parser`, 14.11% in `turso_core::translate`, and 3.64% in the VDBE bytecode builder. These sum to 23.45%; they are user-mode cycle shares, not wall-time attribution. Allocation, copying, index operations, blocking-pool dispatch, and disk I/O also contribute.

Source inspection explains repeated compilation: `SpillSet::spill` calls transaction `execute` for each inserted key, and `SpillSet::contains` calls connection `query` for each disk-backed membership lookup. Turso's convenience methods call `prepare` on every invocation. Both the source and profile support preparing and reusing these statements as the next experiment, followed by the same fsck matrix.

## Fixture construction and correctness

Filesystem import initially made large fixture setup impractical. A sampled import profile was dominated by pin-resource comparisons and B-tree work; the 65,536-file attempt was stopped during setup and yielded no accepted fsck timings. This is a separate import-path finding, not an fsck regression or a production change in this task.

The permanent ignored fixture test constructs a new, exclusively owned repository without an online mutation session. It writes real packed payloads, verifies blob and directory formats, and atomically commits the records, retained root, and physical catalog. It refuses an existing repository. Setup memory and runtime are excluded from fsck measurements. The normal CLI performs all scans and checkout audits.

Every timed sample must exit successfully and report exactly one root, N objects, N payloads, and the original revision, with no issue lines. Each case verifies the expected spill behavior and cleanup. Before and after the matrix, the retained root must match and checkout must reproduce source paths, node types, content hashes, and executable bits. A matrix is complete only after the final checkout audit and binary hash checks. Partial failures remain saved and are rejected by dashboard normalization.

Validation passed: **158 benchmark harness tests**, all-feature/all-target Clippy with warnings denied, formatting, diff whitespace checks, and the new suite through `benchmark all --profile smoke`. All three seeded fixtures passed their full audits. An explicit negative check confirmed that the seeder refuses an existing repository without changing its metadata. Dashboard normalization preserves all 12 variant/size/limit observations, with three samples each and comparable baseline/candidate cohorts.

## Reproduction

Build the CLI in separate baseline and candidate checkouts with the same locked dependencies and compiler profile:

```console
cargo --config 'profile.release.package.casita.codegen-units=256' build -j 2 --release --locked --features cli --bin casita
```

Retain both executables under separate paths. In the benchmark checkout, build the fixture test executable and retain the library-test artifact identified by Cargo's JSON output:

```console
cargo --config 'profile.release.package.casita.codegen-units=256' test -j 2 --release --locked --features cli --lib --no-run --message-format=json
benchmark run fsck --profile standard --repetitions 3 --casita /path/to/fixed-casita --baseline-casita /path/to/baseline-casita --seed-probe /path/to/casita-lib-test --work-dir /new/fixture-directory --output benchmarks/results/fsck-paired.json
```

`benchmark all` supplies the CLI and seeder automatically. Direct runs can omit the seeder to use filesystem import; this may make setup substantially slower. `--reuse-work-dir` reuses retained fixtures while repeating all audits. Smoke covers 321 records, standard covers 8,257 and 65,601, and frontier covers 250,000. All profiles exercise N−1, N, and N+1 limits. The suite is registered in the manifest, all-suite runner, revision comparisons, and dashboard normalization.

The [machine-readable receipt](2026-09-08-fsck.json) embeds the paired results, all raw samples and reports, normalized observations, build identities, dependency lock, benchmark sources, CPU symbol shares, validation logs, and excluded diagnostic attempts.

# GC progress during imports and duplicate readers

The benchmark now records successful GC passes completed during imports
separately from in-flight passes completed afterward. Both use elapsed
completion timestamps from the same monotonic clock. The existing pass and
removal totals remain available; each equals its during/after split.

These counters measure completed passes, not individual deletion times.
Retryable failures can already have removed objects, so successful-pass
removal totals can undercount actual reclamation. An after-import pass may
also have performed some deletions while imports were active.

## Duplicate reader regression

A deterministic repository test opens one unrooted object before marking,
then opens 32 more readers for that same object after marking. It retires
the original reader before pruning. Before the fix, GC rejected the plan
with `Busy("payload pins changed during collection mark")`, despite the
new readers adding no protection.

The pin inventory comparison now compares sets of distinct complete
protections instead of token/protection pairs. Duplicate owners and retired
duplicates do not invalidate a mark. Different scopes, catalogs, and
resources still do. This deliberately does not attempt to prove equivalence
between overlapping scopes or different catalogs.

The repository regression verifies that unrelated garbage is reclaimed
and all readers remain readable. Its negative variant opens the garbage
object after marking and confirms GC still returns Busy and preserves it.
A ledger regression exercises memory, file, and object-store backends:
duplicates preserve the mark, each changed protection component invalidates
it, and the prune fence still rejects new admission and resource growth.
Collection completion removes retired pins normally.

## Measurements

Command:

```sh
cargo --config 'build.build-dir="/tmp/casita-online-holds-build"' bench --features experimental --bench online_holds
```

Default object readers, 30 imports × 16 unique 4 KiB files per scenario.
All four scenarios completed, including final collection, leak checks, fsck,
and byte-verified checkout.

| Scenario | Files/s | Passes during imports | Removed during imports | Passes after imports | Removed after imports | Busy | Retryable errors | Final cleanup removed |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

| imports | 131.38 | 0 | 0 | 0 | 0 | 0 | 0 | 493 |
| imports_readers | 87.07 | 0 | 0 | 0 | 0 | 0 | 0 | 493 |
| imports_gc | 18.77 | 5 | 170 | 1 | 0 | 49 | 23 | 255 |
| imports_readers_gc | 18.53 | 0 | 0 | 1 | 493 | 103 | 0 | 0 |

The combined workload completed **no successful GC passes during imports**.
Its only successful pass finished after imports and reported all 493 obsolete
objects removed. The previous aggregate result could not distinguish this
outcome from progress during continuous writes. Fixing duplicate protection
comparison alone does not resolve the combined workload's contention.

Without readers, five passes completed during imports and reported 170 objects
removed. The 23 retryable failures may have made partial progress: 170 reported
removals plus 255 final-cleanup removals do not account for all 493 obsolete
objects. Do not infer absence of deletion solely from successful-pass counts.

The benchmark currently groups Busy reasons together. Identifying which
remaining conflict dominates the combined workload is the next investigation;
this run does not establish its cause. This is one shared-workstation run,
not a throughput comparison or a proof of starvation under every schedule.

Raw evidence is in the ignored generated directory
`benchmarks/results/online-holds-active-2026-09-08/`: run log, parsed
measurements, executable hash, environment snapshot, and tracked changes.
The during/after sums were checked for every scenario.

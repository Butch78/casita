# CI and performance follow-up, 2026-09-06

Investigated main at `041bacbab44758c78098839690ae38e469e7cb98`.
The immediate priority is CI reliability. The next performance experiment should
combine cache pressure with latency and bandwidth: reduced backend bytes alone
do not establish reduced request latency.

## Catalog lock: reproduced and fixed locally

The [Linux CI failure](https://github.com/cachix/casita/actions/runs/34030094492)
was `catalog_lock_stays_held_until_the_last_writer_clone_finishes`: a fresh file
handle still received `WouldBlock` after the final writer guard was dropped.

`LocalCatalogLock` previously owned `Arc<File>`, relying on the final close to
release the lock. A descriptor inherited by a concurrently forked child can
retain the same open file description until exec or close. This is a lock
lifetime problem even when Rust's last `Arc` has been dropped.

The regression test now retains `File::try_clone()` as a deterministic analogue
of that inherited descriptor. It fails on the old implementation with precisely
the CI assertion, without concurrent tests or sleeps. It also verifies that
dropping the first writer guard does not release the lock while a second writer
guard remains. The actual CI child responsible was not traced; the reproduced
mechanism explains the symptom and is already handled by the repository's
coordination and spill locks.

The fix puts a private file wrapper inside the shared `Arc`. Its destructor
explicitly unlocks before closing, only after the last writer guard finishes.
This retains protection for blocking publication work that outlives a cancelled
caller. Unlocking each clone independently would be incorrect. No test retry or
suite serialization is used to hide the failure.

## Windows RustFS: predates the performance change

Both [the current run](https://github.com/cachix/casita/actions/runs/34030094492)
and [its parent run](https://github.com/cachix/casita/actions/runs/34028275192)
fail during source import in
`rustfs_transfers_payloads_and_publishes_the_root_between_s3_prefixes`.
The failing operation is a PUT of the same content-addressed payload pack,
before transfer or its warm-cache assertions. RustFS exhausts ten client retries
with HTTP 500 `InternalError: File access denied`. Linux passes this S3 case.

The fixture pins RustFS `1.0.0-rc.1`. Its server stdout and stderr were discarded,
so the existing CI log cannot identify the underlying filesystem operation or
Windows error code. The local diagnostic change captures both streams in a
temporary file, enables info logging to stdout, and prints the last 64 KiB on
test panic or startup timeout. Successful tests remain quiet.

Upstream has documented [Windows publication failures under guarded paths](https://github.com/rustfs/rustfs/issues/5757).
Comparing the pinned source with `1.0.0-rc.5` shows substantial changes to Windows
handle-based renames and access/sharing-violation handling in
[`crates/ecstore/src/disk/os.rs`](https://github.com/rustfs/rustfs/blob/1.0.0-rc.5/crates/ecstore/src/disk/os.rs).
This makes a fixture upgrade a plausible experiment, not a verified fix for this
failure. The S3 error text alone does not prove an ACL problem, a path-length
problem, or a particular upstream defect.

Next Windows step: run the same test with retained server diagnostics on rc.1,
then compare against a checksum-pinned rc.5 fixture. Keep the full payload and
assertions. No Windows runner was available locally, and neither the pin nor
the test's coverage was weakened in this investigation.

## Cache pressure: quantified latency risk

The existing measurements use an 8 MiB cache, 32 MiB working set, and 8,192
logical reads of 64 KiB. The warm shuffled scan makes 964 additional backend
requests while saving 612.50 MiB. Warm skewed reads make nine additional requests
while saving 117.17 MiB. Sequential traffic is unchanged.

For an intentionally simplified serial-request model:

```
after_time - before_time = extra_requests * RTT - saved_bytes / bandwidth
```

| Warm access pattern | RTT | Break-even bandwidth | Predicted time change at 8 MiB/s |
|---|---:|---:|---:|
| Shuffled | 25 ms | 25.42 MiB/s | 52.46 s faster |
| Shuffled | 100 ms | 6.35 MiB/s | 19.84 s slower |
| Skewed | 25 ms | 520.74 MiB/s | 14.42 s faster |
| Skewed | 100 ms | 130.18 MiB/s | 13.75 s faster |

Below break-even bandwidth, saved bytes outweigh extra RTTs in this model;
above it, the extra requests cost more. These are predictions for the complete
8,192-read workload, **not measured network timings**. Request overlap, server
latency, transport effects and effective bandwidth can shift the result.
The [model receipt](2026-09-06-followup.json) records exact observed counters,
input hashes, assumptions and derived values.

The current `pack-cache-scale` probe uses a local filesystem. `network-scale`
uses a roughly 1 MiB subtree with an 8 MiB cache. Neither exercises this joint
condition. A useful next matrix is below/above-cache working sets, sequential /
shuffled / skewed reads, RTTs 0/25/100 ms, and rates unlimited/1/8 MiB/s, with
separate concurrency-1 and concurrency-8 cases. Record wall time, p95/p99,
backend bytes, range/whole requests, evictions and in-flight requests, verifying
every payload. Compare identical fixtures on both revisions. Tune promotion
only after that experiment establishes which cases regress.

## Publication and Git OID follow-ups

`publish_current_index` still clones the full chunk index while atomically
capturing its pending mutations. This is a concrete remaining source of work;
its share of the measured 27 ms publication time has not been isolated. Add a
separate snapshot/copy phase measurement before attempting shared immutable
index storage, preserving CAS rebase, concurrent mutation and crash semantics.

Git OID header misses still allocate a reply channel and synchronously wait for
the worker. Header and revision caches share the 8,192-object capacity setting.
A cyclic scan larger than capacity keeps missing; a policy-only FIFO/LRU switch
does not resolve that access pattern. Measure queueing, channel allocation and
state lookup separately, and test both sides of any proposed new cache capacity
with RSS accounting. The earlier SQL experiment was inconclusive and remains
discarded.
